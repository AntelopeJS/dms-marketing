# Extending

Three seams connect other code to the Marketing module: the `@antelopejs/interface-dms-marketing` interface for backend modules, the tracker's JavaScript API for visitor-site code, and the HTTP API.

## Backend modules: the marketing interface

Every `/modules/` page of the DMS is reserved to the platform owner. To show marketing data to tenant users, build your own page and read it through the interface. Declare it in `optionalDependencies`: calls reject when no module implements it, so catch and degrade.

```bash [Terminal]
pnpm add --save-optional @antelopejs/interface-dms-marketing
```

```typescript [src/heatmap.ts]
import { GetInterfaceInstances } from "@antelopejs/interface-core";
import { GetClickHeatmap } from "@antelopejs/interface-dms-marketing";

const isAvailable =
  GetInterfaceInstances("@antelopejs/interface-dms-marketing").length > 0;

export async function pricingHeatmap(tenantId: string) {
  if (!isAvailable) return null;
  return GetClickHeatmap({
    tenantId, // an authenticated tenant id only
    path: "/pricing",
    from: "2026-09-01T00:00:00.000Z",
    to: "2026-09-30T23:59:59.999Z",
  });
}
```

| Field | Description |
| --- | --- |
| `tenantId` | Tenant whose websites are read. Pass an authenticated tenant id only. |
| `path` | Page path exactly as tracked, such as `/pricing`. |
| `from`, `to` | ISO 8601 bounds; each names the day it falls in. Without both, the last 7 days. |
| `websiteId` | One website of the tenant; all of them by default. |

The answer is a `MarketingHeatmapPayload`: `points` (normalised `x` / `y`, a `weight`, and an `anchor` with the clicked element's `selector` and offsets when known), `maxWeight`, `totalClicks`, and `truncated` when the window hit the event cap. Project from `anchor` when you can resolve the selector against the rendered page; `x` / `y` depend on the visitor's window size.

::tip
Keep the page itself backend-declared: compose it from DMS blocks, and make only the heatmap overlay a custom block with `.meta({ name, description, icon })`.
::

## Visitor sites: the tracker API

The tracker installs `window.dmsMarketing` on the tracked site. Guard every call with `?.`: the object is absent when the script is blocked or fails to load.

```javascript [app.js]
window.dmsMarketing?.track("signup_submitted", { plan: "pro" });

window.dmsMarketing?.variation("hero-cta").then((arm) => {
  if (arm === "bold-cta") showAlternateHero();
});
```

- `track(name, data?)` reports a custom event: a name up to 50 characters, optional data up to 4 KiB serialized. Custom events feed the overview and can be funnel steps.
- `variation(key)` resolves to the arm the backend assigned this visitor, and reports the exposure. `null` means "render the control".
- `exposure(experiment, variation)` reports an exposure for integrations that assign arms on their own.

Mark elements that page snapshots must never capture with `data-dms-marketing-mask` (text masked) or `data-dms-marketing-block` (replaced by an empty box). See [Tracker & custom events](/docs/modules/marketing/usage/tracking).

## HTTP API

All routes live under `/api/marketing`. The public ones serve visitor sites; the others need a DMS JWT.

| Route | Auth | Purpose |
| --- | --- | --- |
| `POST /collect` | public | Event ingestion |
| `GET /tracker.js` | public | The tracker script |
| `GET /experiments.js?website=` | public | Per-visitor A/B assignments, as a script |
| `GET/POST/PUT/DELETE /websites` | tenant member / owner | Website CRUD |
| `GET /stats/overview`, `/stats/pages`, `/stats/heatmap` | tenant member | Dashboard, page inventory and heatmap reads |
| `GET /funnels/:id/results` | tenant member | Funnel and A/B computation |
| `GET/PUT /settings` | platform owner | Runtime settings |

The complete route table, with the event, snapshot and assignment contracts, is in [Architecture](/docs/modules/marketing/architecture#http-surface).
