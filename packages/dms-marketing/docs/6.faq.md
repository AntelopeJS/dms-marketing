## No data arrives from my site

Open the site with the browser's network tab and check three things:

1. `tracker.js` loads from your backend.
2. `POST /api/marketing/collect` answers **200**. The table below explains the other answers and the dropped events.
3. The script tag does not use `type="module"`. A module script has no `document.currentScript`, so the tracker cannot read its attributes.

| Collect answer | Meaning and next step |
| --- | --- |
| **403** | The page's host is not the website's domain, one of its extra hosts, or a subdomain of either. Add it with **Allow this host** on the **Websites** page. |
| **404** | The website id is unknown or the site's **Collect data** switch is off. |
| **200**, every event `dropped` | Collection is paused in [Settings](/docs/modules/marketing/usage/settings). The collector also drops a batch without an `Origin` or `Referer` header, a batch from a user agent it reads as a bot, and a batch past the rate limit of the source. |

Step 3 of the install guide runs the same checks for you. See [Verify](/docs/modules/marketing/installation#verify).

## Every visitor looks like the same person

The backend runs behind a reverse proxy that the DMS does not trust. Set the DMS `auth.trustedProxies` to the number of proxies in front of the backend, or set `auth.clientIpHeader` when the hosting platform writes the client address in a header. See [Configuration](/docs/modules/marketing/configuration#settings-from-other-modules).

## The heatmap is empty

Heatmaps record a sample of page loads, 10% by default. Check the sampling on the **Settings** page or the site's `data-heatmap-sample` attribute, and give the page some traffic. See [Pages & heatmaps](/docs/modules/marketing/usage/pages-and-heatmaps#when-the-heatmap-is-empty).

## The heatmap has no page behind it

The backdrop is a page snapshot, which is off by default because it stores page content. Turn on **Page snapshots** in the website's settings, on the **General** tab under **Collect data**. The preview's **Snapshot settings** link opens those settings. Then wait for a sampled visit.

## A setting change does not reach visitors

The tracker script embeds the settings, and browsers cache it for one hour. Returning visitors pick up a change within that hour. While collection is paused, browsers cache the script for one minute, so resuming collection reaches them within a minute.

## Consent depends on your jurisdiction

The module takes these privacy measures:

- It sets no cookie and stores no IP address, user agent or headers.
- It counts visitors with a server-side hash salted every month.
- It honours Do Not Track and Global Privacy Control.

Whether that qualifies for a consent exemption depends on your jurisdiction and your use. The design follows the shape that audience-measurement exemptions ask for, but the compliance analysis stays yours. That holds even more if you enable page snapshots or the GeoIP country dimension.

## Tenant users cannot see these pages

Only the platform owner sees module pages, like every DMS module. To show analytics to tenant users, build a page in your project and read the data through the [marketing interface](/docs/modules/marketing/extending#read-heatmaps-from-a-backend-module).

## The module fails to load after an upgrade

The README compatibility table and `engines["@antelopejs/dms-frontend"]` of `frontend-vue/package.json` set the DMS backend and renderer releases that Marketing runs on. Upgrade the project's DMS backend to a release that implements the `@antelopejs/interface-dms` range of that table, and the renderer to the `engines` range. Otherwise, keep the Marketing release that your current DMS backend supports. [Troubleshooting](/docs/building/troubleshooting) covers dependency resolution and frontend integration errors.

The upgrade notes of each release in the [changelog](https://github.com/AntelopeJS/dms-marketing/blob/main/packages/dms-marketing/CHANGELOG.md) list its behavior changes. Since Marketing 0.5, the module declares the tracker routes to the frontend server, so a tag that points at the dashboard's origin keeps collecting. With an older module on a newer renderer, the frontend server refused those beacons with a **403**.

## Known issues

[KNOWN-ISSUES.md](https://github.com/AntelopeJS/dms-marketing/blob/main/packages/dms-marketing/KNOWN-ISSUES.md) lists the defects found end to end and how each was closed. None is open in this module. Two open ones sit in the DMS core: the breadcrumb of a funnel report skips the funnel list, and the funnel builder shows the browser's own prompt when you leave it with unsaved edits.
